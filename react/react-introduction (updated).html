A more realistic frontend problem

Suppose one page must do all of this for the student collection.

1. Render a list

Show all students returned from the API.

2. Filter while typing

As the search text changes, the visible list should change immediately.

3. Show selected details

Clicking one student should update the details area on the same page.

The important part

This is not a one-time DOM task. The page keeps changing. Search text changes. The filtered list changes. The selected student changes. This is exactly the kind of UI React is good at.

Plain JavaScript approach

With vanilla DOM code, we must manually keep the UI in sync. That is where things become repetitive and fragile.

What React removed from our job
  • No document.createElement()
  • No innerHTML = ""
  • No manual renderSelectedStudent() call
  • We update state; React updates the page
The mental model to remember

UI = f(state). Read that as: the UI is a function of the current state. When state changes, React runs the component again and updates the page to match.

So what is React, exactly?

It is a library

React is a JavaScript library for building user interfaces.

It builds with components

You break the page into reusable pieces like <SearchBox /> and <StudentList />.

It renders from data

You describe the UI from data instead of manually editing DOM nodes all over the page.

It is UI-focused

React mainly handles the interface layer. The backend, database, and API still stay separate.

Where the next ideas come from

If React builds UI from components, then the next questions naturally become: what do components return, how do they receive data, and how do they react to change?

Why people like it

The UI structure is easier to read because it looks close to HTML.

Why it is powerful

It still lives inside JavaScript, so we can use variables, expressions, arrays, and functions.

What actually runs

Tools like Babel translate JSX into JavaScript code that describes the UI.

Rule 1

Use className instead of HTML's class.

Rule 2

Use { } when you want to place JavaScript inside JSX.

Rule 3

A component returns one root element, or a Fragment like <>...</>.

State: data that can change over time

Props come from the parent. State lives inside a component and changes over time. When state changes, React re-renders the component.

const [state, setState] = React.useState(initialValue);
state = current value
setState = function used to update it

useState()

The standard way to store changing data in a function component.

Initial value

The value used the first time the component renders.

Setter function

Call it to update the state and trigger a re-render.

Main rule

Never mutate state directly. Always use the setter function.

How this fits our course project

Earlier, the frontend could be a plain index.html plus a JavaScript file. In React, most UI logic moves into App.jsx and other components, and later those components can call the Express API you already built.

HMR: why editing React feels fast

Vite gives us Hot Module Replacement. Save a file, and the browser updates almost immediately without a full reload.

1. Edit

Change something in App.jsx or another component.

2. Save

Vite notices the file changed.

3. Replace

Only the changed module is updated in the browser.

4. Continue

You keep testing without a slow full refresh cycle.

Without HMR

Edit, reload, navigate back, re-enter test values, and rebuild the same UI state again.

With HMR

Edit, save, see the result almost instantly. This makes learning and debugging much easier.

Summary

Why React?

Because changing pages are easier to manage when the UI is described from data instead of manually patched in the DOM.

What is JSX?

HTML-like syntax inside JavaScript, with JavaScript expressions placed inside { }.

What are components?

Reusable UI functions that return JSX.

What are props?

Read-only inputs passed from parent to child.

What is state?

Changing data inside a component that triggers re-rendering.
