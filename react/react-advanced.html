Controlled forms: the idea

A controlled input is one whose value is always driven by React state — not by the DOM. React owns the value, so it is always in sync with the rest of the component.

1. Create state:  const [name, setName] = useState("")
2. Bind state to the input:  value={name}
3. Update state on every keystroke:  onChange={(e) => setName(e.target.value)}

Uncontrolled input (avoid)

No value prop, no onChange. The DOM holds the value. You read it later with ref.current.value or event.target.value only on submit. React has no awareness of what the user is typing between keystrokes.

Problem: you cannot validate as the user types, you cannot disable a button based on what is in the field, and you cannot show a live preview.

Controlled input (use this)

The value prop comes from state. Every keystroke fires onChange, which calls the setter, which triggers a re-render with the new value shown in the input. React is always the source of truth.

Benefit: you can validate in real time, disable the submit button until the form is valid, and read all field values directly from state at any moment.

useEffect: code that runs after React updates the screen

A React component does two different jobs:

Job 1: Render the UI

The component returns JSX that describes what should appear on the page. This part should stay predictable: same state + same props → same JSX.

Job 2: Do outside work

Some work is not just "draw the UI." Examples: fetching data, starting a timer, or changing the browser tab title. That work goes in useEffect.

Simple idea

useEffect lets you say: "After React finishes updating the page, run this extra code."

Example: update the browser tab title

📄 Example.jsx
import { useEffect, useState } from 'react'

function Counter() {
  const [count, setCount] = useState(0)

  useEffect(() => {
    document.title = `Count: ${count}`
  }, [count])

  return (
    <div>
      <h2>Counter</h2>
      <p>Current count: {count}</p>
      <button onClick={() => setCount(count + 1)}>Increase</button>
    </div>
  )
}

export default Counter
What happens here: the component renders the button and the number. After the render finishes, useEffect runs and updates the browser tab title. When count changes, React renders again, then the effect runs again with the new value.

What is the dependency array?

The dependency array is the second argument to useEffect:

useEffect(() => { /* effect code */ }, [count])
Definition

The dependency array is a list of values that React should watch. If one of those values changes, React runs the effect again after the next render.

Three common patterns

Code What it means Simple example
useEffect(() => { ... }) Run after every render Usually avoid this unless you truly need it every time
useEffect(() => { ... }, []) Run once after the first render Fetch initial data when the page first loads
useEffect(() => { ... }, [count]) Run after the first render, and again whenever count changes Update the tab title whenever the counter changes

One more example: fetch data once when the component first appears

📄 StudentDirectory.jsx
useEffect(() => {
  async function loadStudents() {
    const response = await fetch('http://localhost:3000/students')
    const data = await response.json()
    setStudents(data)
  }

  loadStudents()
}, [])
The empty dependency array [] means: run this effect once when the component first appears. That is why it is a common pattern for an initial fetch.
Important distinction

Rendering answers: "What should be shown on the page?"
useEffect answers: "After the page updates, what extra work should happen?"

📄 src/components/StudentDirectory.jsx
import { useEffect, useState } from 'react'

function StudentDirectory() {
  const [students, setStudents] = useState([])
  const [loading, setLoading] = useState(true)
  const [error, setError] = useState('')

  useEffect(() => {
    async function loadStudents() {
      try {
        const response = await fetch('http://localhost:3000/students')
        if (!response.ok) {
          throw new Error('Request failed')
        }
        const data = await response.json()
        setStudents(data)
      } catch (err) {
        setError(err.message)
      } finally {
        setLoading(false)
      }
    }

    loadStudents()
  }, [])

  if (loading) return <p>Loading...</p>
  if (error) return <p>Error: {error}</p>

  return (
    <ul>
      {students.map((student) => (
        <li key={student._id}>{student.name} — {student.major}</li>
      ))}
    </ul>
  )
}

export default StudentDirectory
The empty [] means the fetch runs once after the first render. Three state variables handle the three possible outcomes: loading, error, and success. The finally block runs after either try or catch, ensuring loading is always set to false.

Cleanup: stop work when the component changes

Some effects must clean up after themselves. If you start a timer in useEffect and do nothing else, the timer keeps running even after the component is removed — causing duplicate ticks and confusing bugs.

📄 src/components/SessionTimer.jsx
import { useEffect, useState } from 'react'

function SessionTimer() {
  const [seconds, setSeconds] = useState(0)
  const [running, setRunning] = useState(false)

  useEffect(() => {
    if (!running) return        // do nothing when paused

    const intervalId = setInterval(() => {
      setSeconds((prevSeconds) => prevSeconds + 1)
    }, 1000)

    return () => clearInterval(intervalId)   // cleanup function
  }, [running])

  return (
    <div>
      <h2>Session Timer</h2>
      <p>{seconds}s</p>
      <button onClick={() => setRunning(true)}>Start</button>
      <button onClick={() => setRunning(false)}>Stop</button>
      <button onClick={() => { setRunning(false); setSeconds(0) }}>Reset</button>
    </div>
  )
}

export default SessionTimer
The function returned from useEffect is the cleanup. React calls it before running the effect again (when running changes) and when the component unmounts. clearInterval(intervalId) stops the specific interval that this effect created.

Why cleanup matters — step by step

  • User clicks Start → running becomes true → effect runs → interval starts, counting up every second.
  • User clicks Stop → running becomes false → React calls the cleanup function → clearInterval stops the old interval → effect runs again but returns immediately because !running is true.
  • Without the cleanup: clicking Stop would not actually stop the old interval. Clicking Start again would create a second interval running on top of the first. The counter would count at double speed.
How to test cleanup is working

Click Start, let it count for a few seconds, click Stop — the counter freezes. Click Start again — it resumes from where it stopped, not at double speed. If it counts faster and faster each time you Start/Stop, the cleanup is broken.

Redux: When local state stops being enough

Local state is the right tool when exactly one component owns and uses a piece of data. The problem arises when two or more components need to read or update the same data.

The problem: "prop drilling"

Suppose RegistrationForm adds a student and you want StudentDirectory to immediately show the new student. With local state you have to lift state into App, then pass it down as props to both components. As the tree gets deeper, props must pass through components that do not even use them — this is called prop drilling and it becomes unmanageable quickly.

The solution: global store

Redux provides a single store that sits outside the component tree. Any component at any depth can read from it with useSelector or write to it with useDispatch. No props need to be threaded through intermediate components.

Practical rule: do not over-use Redux

Start with local state. Only promote data to the Redux store when two or more distant components genuinely need to share it. Form field values, loading spinners, and open/closed menus almost always belong in local state.

Redux key concepts

Redux introduces a few small concepts that work together. The good news is that each one has one job. Once those jobs are clear, the code becomes much easier to read.

Store

The central box that holds shared state.

Action

A plain object that describes what happened.

Reducer

A function that receives the old state and the action, then decides the new state.

Slice

A slice is one small part of your Redux state plus the code that updates that part.

The big picture

A component does not directly edit the store. Instead it dispatches an action. Redux sends that action to a reducer. The reducer returns updated state. Then components read the new state and re-render.

Redux key concepts (continued)

Before touching files, lock in these three ideas. Everything else is built on top of them.

1. Shared state lives in one store

Instead of scattering one shared value across many components, Redux keeps it in one place.

2. Components describe changes with actions

A click does not directly mutate state. It dispatches an action that says what happened.

3. Reducers decide the next state

The reducer reads the action and returns the updated state.

4. Components read the result

useSelector reads the latest store state, and React re-renders the UI.

Good mental model

Think of Redux like a front desk for shared data. Components do not sneak into the office and change records directly. They submit a request, the rule system processes it, and then everyone sees the updated record.

What exactly is the store?

The store is the object that holds your global state. In this deck, the shared state is a students section containing the student list and the currently selected student.

📄 Concept only
{
  students: {
    list: [
      { id: 1, name: 'Ava', major: 'IST' },
      { id: 2, name: 'Noah', major: 'CS' },
      { id: 3, name: 'Liam', major: 'Data Science' }
    ],
    selected: null
  }
}
This is not a separate file. This is the shape of the data that will end up inside the Redux store once everything is wired together.

students

The top-level key for this slice of global state.

list

The array of students that every interested component can read.

selected

The one student the user most recently chose, or null if none is selected.

What is an action?

An action is just a plain JavaScript object that describes something that happened. It does not change state by itself. It only carries information to the reducer.

📄 Concept only
{
  type: 'students/selectStudent',
  payload: { id: 2, name: 'Noah', major: 'CS' }
}
The type string says what happened. The payload carries extra data needed for the update. In this case, the payload is the student that was clicked.

type

A label for the event. Reducers use it to decide which update logic should run.

payload

The extra data that travels with the action. Some actions need it, some do not.

What is a reducer?

A reducer is a function that receives the current state and an action, then decides what the next state should be. In Redux Toolkit, the reducer logic is written inside a slice.

📄 Concept only
selectStudent(state, action) {
  state.selected = action.payload
}
This reducer says: when the selectStudent action arrives, copy the student from action.payload into state.selected.

What is a slice?

A slice is Redux Toolkit's way of grouping related Redux pieces together in one file. One slice usually represents one feature or one logical section of the app's state.

name

A label such as 'students'. Redux Toolkit uses it when creating action type strings.

initialState

The starting value for this section of the store.

reducers

The update rules for this slice. Redux Toolkit also auto-generates action creators from these reducer names.

Why this is useful

Without createSlice, you would manually write action type strings, action creator functions, and reducer switch statements in different places. A slice keeps them together so the feature is easier to follow.

createSlice({ name, initialState, reducers: { ... } })

import { createSlice } from '@reduxjs/toolkit'

const initialState = {
  list: [
    { id: 1, name: 'Ava', major: 'IST' },
    { id: 2, name: 'Noah', major: 'CS' },
    { id: 3, name: 'Liam', major: 'Data Science' },
  ],
  selected: null,
}

const studentsSlice = createSlice({
  name: 'students',
  initialState,
  reducers: {
    selectStudent(state, action) {
      state.selected = action.payload
    },
    clearSelection(state) {
      state.selected = null
    },
  },
})

export const { selectStudent, clearSelection } = studentsSlice.actions
export default studentsSlice.reducer
This one file gives you three things at once: the initial state, the reducer logic, and the generated action creators selectStudent and clearSelection.

Unpacking studentsSlice.js line by line

Do not treat the slice file as magic. Each part maps directly to one of the concepts you just learned.

initialState

This becomes the starting value under state.students once the slice is added to the store.

name: 'students'

This helps build action type strings such as students/selectStudent.

selectStudent

A reducer case that copies action.payload into selected.

clearSelection

A reducer case with no payload. It just resets selected to null.

Two exports, two different purposes

studentsSlice.actions gives you action creators to dispatch from components. studentsSlice.reducer is the reducer function that the store needs to register.

Why do we still need store.js?

The slice defines one piece of Redux logic, but nothing uses it yet. The store is where all slices are registered so Redux knows the full global state tree.

store = configureStore({ reducer: { students: studentsReducer } })

Left side: students

The state key. This is why you later read from state.students.

Right side: studentsReducer

The reducer function exported from the slice file.

Key takeaway

A slice defines a feature. The store combines features into one global state object.

Before components can use Redux: Provider

You now have a Redux store object, but React components still cannot see it yet. Provider is the bridge that makes the store available to the whole component tree.

<Provider store={store}> <App /> </Provider>

Why wrap high in the tree?

Any component below Provider can use useSelector and useDispatch. Placing it in main.jsx covers the entire app.

What if you forget it?

Components that try to use Redux hooks will throw an error saying React Redux context was not found.

Reading from the store with useSelector

useSelector lets a component read data from the Redux store. You pass it a function that says which piece of the state you want.

📄 Concept only
const students = useSelector((state) => state.students.list)
const selected = useSelector((state) => state.students.selected)
The parameter named state is the entire Redux store state object. Your selector function picks out only the part this component needs.

First selector

Reads the student array from state.students.list.

Second selector

Reads the currently selected student from state.students.selected.

Automatic re-render

If the selected piece of state changes, React re-renders this component with the new value.

Writing to the store with useDispatch

useDispatch gives a component the dispatch function. That function is how the component sends actions into Redux.

📄 Concept only
const dispatch = useDispatch()

dispatch(selectStudent(student))
dispatch(clearSelection())
selectStudent(student) creates an action object with a payload. clearSelection() creates an action object without one.
Important distinction

selectStudent is an action creator function. Calling it creates an action object. dispatch(...) is what actually sends that action to Redux.

New file: src/features/students/StudentList.jsx

This component uses both Redux hooks together: useSelector to read store data and useDispatch to send updates.

📄 src/features/students/StudentList.jsx
import { useDispatch, useSelector } from 'react-redux'
import { clearSelection, selectStudent } from './studentsSlice.js'

function StudentList() {
  const students = useSelector((state) => state.students.list)
  const selected = useSelector((state) => state.students.selected)
  const dispatch = useDispatch()

  return (
    <div>
      <h2>Students</h2>
      <ul>
        {students.map((student) => (
          <li key={student.id}>
            <button onClick={() => dispatch(selectStudent(student))}>
              {student.name} — {student.major}
            </button>
          </li>
        ))}
      </ul>

      <button onClick={() => dispatch(clearSelection())}>Clear selection</button>

      <p>
        {selected
          ? `Selected: ${selected.name} (${selected.major})`
          : 'Selected: none'}
      </p>
    </div>
  )
}

export default StudentList
This is the full Redux cycle in one component: read students from the store, render buttons from that data, dispatch an action when a student is clicked, and read the updated selected value back from the store.

Summary

React DevTools

Install from the browser extension store. Use the Components tab to inspect live React state and props while the app is running.

Controlled forms and effects

Local state is still the default tool for component-specific logic such as form fields, loading flags, and timers.

Redux vocabulary

Store holds shared state. Action describes what happened. Reducer decides the next state. Slice groups a feature's state and reducers together.

Redux workflow

Create a slice, register it in the store, wrap the app in Provider, read with useSelector, and update with useDispatch.
